# CRT.Server version history

The version this service reports from `GET /api/health`, and why each number changed.

**This file is maintained by Claude, not by hand.** The project owner asked (2026-09-26) for the
server's version to be handled for them: they bump CRT themselves, but this one
is to be judged and bumped by whoever changes the server. So when you change anything under
`src/CRT.Server/`, you decide the bump, edit `InformationalVersion` in
[CRT.Server.csproj](CRT.Server.csproj), and add the line here. There is nothing else to remember -
the `Stop` hook [server-version-bump.sh](../../.claude/hooks/server-version-bump.sh) names this
file and the csproj when server code changed and neither moved.

## The rule: SemVer 2.0.0, judged on the HTTP API

The version describes **the API contract and the behaviour a caller depends on**, not the size of
the diff. CRT (its submissions, and its Maintainer tab) talks to this service over the wire, and is not rebuilt
when the server is, so the question is always *"what would break, or newly work, for a client
already installed?"*

| Bump | When | Examples |
| --- | --- | --- |
| **MAJOR** | A client that worked against the previous version can now fail. | A route renamed or removed; a JSON field renamed, removed or retyped; a field becoming required; a status code changing meaning; a rule that starts refusing what it used to accept (a narrowed file-type allowlist, a new mandatory approval). |
| **MINOR** | New behaviour, every existing client keeps working. | A new route; a new optional request field; a new field ADDED to a response (readers ignore unknown fields); a new migration that only adds tables or nullable columns; a rule that starts accepting more than it did. |
| **PATCH** | A defect fixed, or a change no caller can observe as new behaviour. | A wrong status code corrected to what the contract already promised; a crash or a leak fixed; a mail body reworded; a comment, a test, a log line; an internal refactor with the same observable behaviour. |

Three judgement calls that come up in this codebase specifically:

- **A DATABASE migration is not automatically a MINOR.** Judge it by what the API does with it. A
  migration that only backs a new endpoint is MINOR; one that renames a column the API already
  exposed under a name that now changes is MAJOR; one that fixes a column type nothing depended on
  is PATCH. Migration 0010 (renaming `reviewers` to `maintainers`) was PATCH-shaped on the wire and
  MAJOR-shaped in the vocabulary - it landed pre-release, which is why it cost nothing.
- **Tightening a security rule is MAJOR even when it is correct.** Refusing a file type that used
  to be accepted breaks a contributor mid-submission. It should still be done - it just has to be
  visible as a break.
- **A change ONLY to `CRT.Data` still bumps this service** when the server's behaviour changes with
  it, because the two are deployed as one binary set. `CRT.Data` carries no version of its own.

**The pre-release escape hatch is spent.** Up to `1.0.0-alpha.3` a MAJOR-shaped change bumped the
alpha counter, on the grounds that nothing was released so nothing could break for a caller that
existed. The version is now `1.0.0`, so the table above applies literally: the next breaking change
is `2.0.0`. Do not reintroduce an `-alpha.N` suffix to avoid a major bump - if the API breaks, say
so in the number.

## What a client sees

`GET /api/health` answers `{"status":"ok","version":"1.0.0","utc":"..."}`. The `+<commit>`
build metadata the .NET SDK appends is stripped before it goes out - the endpoint is unauthenticated
and publicly reachable, so it must not publish the exact source commit. That is
`HealthReport.NormaliseVersion`, pinned by `HealthReportTests`.

To read the deployed version:

```
curl -s http://127.0.0.1:5199/api/health
```

## History

Newest first. One line per version, saying what a caller would notice.

| --- | --- | --- | --- |
| `3.6.0` | 2026-09-29 | MINOR | Code review fixes. **A board copied to production by hand no longer blocks its system**: the one-in-BETA rule refused every approval of a system whose record said it waited for production, which a hand-copied board did for ever. When the record says "waiting", the approval and `GET /api/review/production` now compare the trees; production already holding BETA's state is recorded as in production (audited as `production.found_in_place`, a new event in a system's history) - a rule that accepts more, so MINOR. **"returned" is recorded** (migration **0015**, `submission_beta_returns`): a push-back stores when it returned each submission, and a submission reads as `returned` only while pending with no later decision - no longer merely "pending with a comment". Submissions returned before 0015 now read as `pending`. **Defects fixed:** a board-view text cut at its column limit could split a character in two, which the database refused, failing the whole batch for ever (`BoardViewRules.Clip`); the production panel, the push-back mail and the "now in production" mail used the contact address only and so missed every signed-in contributor - they now use the account's address; a failed ip-api.com lookup is followed by five minutes without lookups instead of a 3-second wait on every board-view request. `GET /api/review/production` asks a fixed number of queries however many systems wait. No route or field removed or required. |
| `3.5.1` | 2026-09-29 | PATCH | **Wording only** - the separate CRT Maintainer application became a Maintainer tab in CRT. No route, field, rule or migration changed. |
| `3.5.0` | 2026-09-28 | MINOR | **"Reject" on Beta > Prod** (owner request): `POST /api/review/production/rollback` takes an optional `reject` (default false). With it, the rollback moves BETA exactly as a push-back does, but every submission it takes out becomes `rejected` with the comment instead of `pending`, its contributor gets the ordinary rejection mail rather than the returned-to-queue one, and the audit row is `beta.rejected` (a new event in a system's history). The answer gains `rejected` (false when it pushed back), so a client can tell an older server that ignored the flag. Also a defect fixed (owner report): **an approval keeps the workbook's `# Hardware:` / `# Board:` caption.** The rows never carried it and the publish left it out, so every sheet of a workbook approved into BETA lost its first two lines. The board being replaced gives it now; a board without one - a new system, or one published before this fix - takes the names it is listed under in the drop-down lists. |
| `3.4.0` | 2026-09-28 | MINOR | **A system's file tree** (owner request). A new route, `GET /api/review/submissions/{id}/files`, answers CRT.Data's `SubmissionFilesAnswer`: every file of the system as the BETA data will hold it after approving - its own folder and the shared files it uses - each with what the approval does to it (`unchanged`, `added`, `changed`, `removed`) and where it can be opened from, plus BETA's public data address. Same authority as the submission detail. `POST /api/review/production/plan` gains three optional fields: `unchangedFiles` (the paths `unchangedCount` counts), `betaDataUrl` and `productionDataUrl`. **A board's highlight file is written only when its content changes**: a publish whose highlights and calibrations read the same as the file already there keeps it byte for byte, so the first publish of a board no longer "replaces" a hand-made `.json` that only differs in layout, and "Publish to production" no longer lists it. Nothing removed or required. |
| `3.3.1` | 2026-09-28 | PATCH | Defect fixed (owner report): **a file copied into the data by hand no longer breaks a publish.** After production's files were copied into BETA as root, "Approve and publish to BETA" answered a bare 500 - the highlight file (`.json`) beside a board was opened for writing, which a root-owned file refuses, and the new workbook had already been written. Every board file is now written beside itself and renamed into place, which needs only its folder; and a publish, a production promotion and a push-back each check every folder they will write into BEFORE writing anything, refusing with a sentence naming the folders ("nothing was changed") where they used to stop part-way - the command that gives the service its folders back is in the log. A highlight file that still cannot be written is reported as a part-publish (400) instead of escaping as a 500. No route, field or migration changed. |
| `3.3.0` | 2026-09-28 | MINOR | **A contributor discarding their own draft is recorded and shown** (owner request). A new contributor route, `POST /api/submissions/{id}/draft-discarded` (no body, the `X-Submission-Token` header as on the status check; `204`, or `404` for no such submission or a token that does not match), records the FIRST notice per submission in `submission_draft_discards` (migration 0014) and audits it as `submission.draft_discarded` under `#{id}`. New optional fields, nothing removed or required: `draftDiscardedUtc` on each review queue entry and on the detail's `submission`, on each carried submission of the production plan and on each submission of `POST /api/review/systems/detail`; `carriesDiscardedDraft` on each `GET /api/review/production` entry; and the system's `history` shows the event. |
| `3.2.1` | 2026-09-27 | PATCH | Defects fixed, with the code review's findings folded in before it was deployed. **"Push back to queue" no longer takes a promoted board out of BETA when production's copy cannot be read** (a missing or renamed folder, a mount that is down): "never promoted" now comes from the system's record, not from an empty folder, and such a system is refused with 409 and nothing changed - where it used to wipe the board from BETA and its lists. **The BETA checksum manifest is rebuilt one at a time**, each with its own temporary file: a placement saved in the same second as a publish could interleave the two writes. **Two always-empty fields left the rollback answers**: `sharedRemovalCandidates` (the plan) and `sharedKept` (the result) - a rollback never removes a shared file, and every reader already took a missing list as empty. **A start that fails in the database no longer crashes**: a failed or refused migration logs its reason at crit and exits with 78, which the unit already does not restart (the first deploy of 3.2.0 crash-looped with a core dump every five seconds over a table made by hand); an unreachable database exits with 69 and is restarted as before, without the core dump. **Under systemd the log is written in systemd's format** - one line per entry, its level recorded - so `journalctl -p warning` now shows the service's own warnings and errors; before, the journal filed every line as info. |
| `3.2.0` | 2026-09-27 | MINOR | **Board views** (owner request): a new anonymous route, `POST /api/usage/board-views`, takes a batch of views from CRT (CRT.Data's `BoardViewReport`) and stores one row per view in `crt_board_views` (migration 0013) with the board's published names, version, OS, CPU, BETA source and country - looked up from the sender's address at ip-api.com, the address not stored. `202` stored (or a batch already stored), `400` a report to drop, `429` over 60 batches an hour from one address (counted in memory).
